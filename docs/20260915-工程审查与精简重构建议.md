# ArbiGuard 工程审查与精简重构建议

## 1. 范围与结论

- 日期：2026-09-15。
- 工作目录：`E:\contract\ArbiGuard`。
- 基线：本地 `dev` 分支，提交 `f97f902`，开始审查时工作树干净。
- 范围：25 个 Erlang 模块，以及管理端、配置、启动和交易文档。
- 本轮只检查、隔离复现和提出方案，未修改业务源码、配置和账户数据，未访问远程仓库或交易所，未执行真实交易。
- 本文是待确认建议，不表示已经重构、已经稳定或已证明盈利。

**结论：当前系统没有可信的实盘执行闭环，模拟成交、账户余额和收益也不能作为策略有效性的依据。根因不是简单的代码冗长，而是同一事实存在多个不一致的表示，订单与持仓没有贯穿生命周期的可靠所有者，错误又常被转换为成功、默认值或空数据。**

实际机会链路为 `scanner -> opportunity ETS -> 各 open_executor 轮询`，与部分旧文档的账户路由推送描述不一致。自动实盘提交只生成“等待成交”的本地结果，没有发交易所订单；测试下单和 REST 账户快照明确未实现。下文实盘问题属于代码缺陷及接入风险，没有证据表明已经造成真实资金损失。

## 2. 优先修复的问题

### P1-01 实盘未发送订单，却进入等待成交

证据：`src/exchange/arbiguard_live_order.erl:28`、`:40`；`src/exchange/arbiguard_live_adapter.erl:28`、`:37`。

非空凭据即可使自动开仓、平仓、撤单返回 `awaiting_fill/pending_real_adapter`，但没有网络请求或实际下单任务。测试下单固定拒绝，账户快照固定返回未实现。

后果：执行器等待不会自然到来的回报，管理端呈现超出实际能力的执行状态。应删除假受理；未实现明确拒绝。真实提交后区分“确认接受”与“结果未知”，超时先按稳定客户端订单 ID 查询，不能换 ID 盲目重试。

### P1-02 展示转换破坏运行状态

证据：`src/execution/arbiguard_open_executor.erl:449`、`:367`、`:722`；`src/execution/arbiguard_close_executor.erl:258`、`:362`、`:748`。

`public_order/1` 删除 `req/opportunity` 或 `req/position`，返回值却继续用于提交和写回内部订单。下一次回报、重试或平仓丢失策略、账户元信息、机会和持仓，只能落入默认值。

应将运行状态与 HTTP 展示对象分开。展示转换只能在查询出口执行，不得写回交易状态；内部缺失必需字段要暴露错误，不能静默补空 map。

### P1-03 正常的余额拒绝导致执行器崩溃

证据：`src/account/arbiguard_state.erl:55`、`:217`；`src/execution/arbiguard_open_executor.erl:321`。

余额不足时账户返回 `opened_position => undefined`，执行器仍将其作为 map 读取费用，复现为 `badmap, undefined`。另一个错误路径中，账户调用退出被 `catch` 吞掉后仍继续构造“成交”；平仓同样忽略账户调用结果并设置 `filled_paper_close`（`arbiguard_close_executor.erl:225`）。

应使用明确的成功、业务拒绝、基础设施故障结果。只有对应账本事务成功，才能推进成交状态，不能将失败包装为成交。

### P1-04 模拟成交超出盘口，重复操作破坏资金守恒

证据：`src/account/arbiguard_state.erl:47`、`:199`、`:288`、`:298`；`src/execution/arbiguard_open_executor.erl:328`。

- 本批盘口仅允许 100，账户却读取总目标 1000 并按 1000 开仓；执行器随后又按 100 标记完成。
- 同一 ID 开仓两次会重复扣保证金并覆盖原持仓，没有账本级唯一性保护。
- 平仓找不到已存持仓时使用请求持仓兜底，重复平仓再次返还保证金。复现 10000 本金变为 10200。
- 开仓终态订单过期清理不能替代持仓唯一性约束；清理旧订单后仍可能再次开相同组合。

应让账本只消费明确成交事实，在同一事务内完成去重、持仓唯一性、数量和余额更新。不存在的持仓不得用请求对象补建并结算；模拟器不再自行决定目标仓位。

### P1-05 无深度、旧盘口和错误行情仍可执行

证据：`src/execution/arbiguard_open_executor.erl:525`、`:612`、`:654`；`src/execution/arbiguard_close_executor.erl:381`、`:808`；`src/exchange/arbiguard_exchange_ticker.erl:423`、`:500`、`:625`。

- 执行器不检查报价年龄；`max_order_book_age_ms` 配置未被执行路径读取。时间戳为 1 的报价仍可通过检查。
- 数量为零或缺失时，盘口可成交量反而被设为整个目标；零深度可以“成交”100 万名义额。
- Binance 解码后的 atom `'B'/'A'` 未被数量读取候选包含；`best_size` 的整数 `0` 分支不匹配 `0.0`，有效 BBO 数量可能读成零。
- 新盘口归零时 `positive_or_prev` 保留旧价格和数量，同时刷新 `updated_at`，使旧流动性看起来新鲜。
- 执行器本地缓存优先于 ETS；首次 BBO 无 mark 时又可能用零覆盖 REST 中的有效标记价。

应删除旧值拼接和重复缓存。市场接收边界按频道维护盘口、标记价及各自时间与连接代次；执行前检查新鲜度、双边时差和真实深度。未知深度不是无限深度，标记价不能冒充可成交价。

### P1-06 成交身份、数量单位和幂等均不可靠

证据：`src/exchange/arbiguard_private_ws.erl:227`、`:295`；`src/execution/arbiguard_open_executor.erl:108`、`:771`；`src/execution/arbiguard_close_executor.erl:751`。

- 回报有 `order_id/client_order_id`，消费者按 `id/parent_id` 找父单；即使找到 owner，路由仍丢弃已查到的本地订单记录。
- `accFillSz` 被当成交金额、`sz` 被当实际成交数量，状态仅转小写，未做精确协议映射。
- 同一笔 60 回报两次，累计变成 120；部分成交直接移除整个 pending 子单。
- 两腿共用一个确认金额，不能可靠区分哪条腿成交、剩余数量和单边暴露。

应按交易所和频道明确解析，两腿分别记录订单身份、累计成交量、成交 ID、成交均价、费用和终态。累计回报只应用新增部分，旧回报不能倒退状态。跨交易所 FOK 不具备原子性，两腿必须独立确认。

### P1-07 实盘持仓缺少关键事实，平仓 ID 和目标反复变化

证据：`src/execution/arbiguard_open_executor.erl:785`、`:851`；`src/execution/arbiguard_close_executor.erl:126`、`:144`、`:294`、`:367`、`:765`。

`order_to_position/1` 不保留两腿开仓均价和数量。跟踪对象使用 `|position` ID，平仓对象改为 `|close`，但 `maps:map` 保留原外层键，回报按新 ID 无法找到原状态。分批平仓把总目标改成剩余量后，又减去累计成交量：目标 100、已成交 40，本来剩余 60，最终只剩 20 可提交。

应使用贯穿生命周期的稳定组合 ID 和同一个状态所有者。总目标不可随分批执行缩写，平仓量来自实际剩余持仓数量，而不是重新估算的入场名义额。

### P1-08 账户隔离、凭据与停止语义错误

证据：`src/execution/arbiguard_open_executor.erl:95`、`:163`、`:864`；`src/account/arbiguard_account_manager.erl:99`、`:324`、`:666`；`src/account/arbiguard_exchange_account.erl:18`。

- 全部账户读取同一机会快照，扫描请求可以覆盖进程已经绑定的账户和模式。
- 实盘仓位限额读取全局模拟持仓数，不是所属实盘账户持仓。
- `desk-a` 和 `desk_a` 被转成同一个进程注册名称，可能复用交易所账户进程并覆盖凭据。
- 初始 token 归一化使用 `#{}` 模式判断空 map，但该模式匹配所有 map，合法 token 全被过滤。
- 关闭 live 同时终止开仓和平仓执行器，已有仓位失去风险管理所有者。

应以精确账户键管理 PID，账户身份不可被扫描参数覆盖；凭据只由对应接入进程持有。“禁止新增交易”必须保留已有仓位管理，不能等同于停止所有执行进程。

### P1-09 逐腿账本和对冲数量口径错误

证据：`src/account/arbiguard_state.erl:111`、`:221`、`:307`、`:317`、`:563`。

新增模拟交易所只增加新余额、不扣减已有资金；本金 10000 变成 13333.33。平仓将价差盈亏、资金费和费用平均分给两家交易所；应为 A 盈利 100、B 亏损 100 时，两边余额却均回到原值。

两腿采用相同 USDT 名义额分别除以各自价格，基础币数量并不相同。100/110 价格、各 1000 名义额会留下 0.90909 基础币数量差。若目标是基础币数量中性，该实现不能称为已充分对冲；若目标是美元名义中性，也必须明确记录剩余价格风险。

应逐腿核算余额、保证金、费用、资金费和盈亏，总账只求和，不均分。先统一标的和合约乘数，再选择符合双边规格的共同基础币数量。

### P1-10 风险退出被盘口门槛阻塞，超时不独立运行

证据：`src/execution/arbiguard_close_executor.erl:77`、`:317`、`:390`、`:468`、`:552`。

先要求双边盘口能满足整个目标，再运行爆仓、资金费和下架判断。盘口不足直接 `wait`，风险判断根本不会执行。所谓 500 毫秒紧急处理只在下一次 ticker 到达时比较时间，没有独立定时器；断流时不会如期触发。

应将风险判断与普通择机平仓分开，用定时器处理断流、暴露时限和结算。按明确风险策略分批 reduce-only 退出；缺少可执行行情不能伪造成交，也不能无限等待下一条行情。

### P1-11 重启不是恢复，现有恢复逻辑还会漏掉单边仓位

证据：`src/account/arbiguard_account_manager.erl:72`、`:234`、`:340`、`:546`；`src/execution/arbiguard_close_executor.erl:41`；`src/account/arbiguard_state.erl:31`。

账户管理器自行 `start_link` 工作进程，捕获退出后只写日志、不重启。管理器重启仅创建默认账户；执行器初始化为空，模拟账户重新初始化本金。ticker 重启清空订阅，现有消费者没有可靠重登记机制。

账户持仓“恢复”按第一个异所反向持仓猜配对，没有按数量拆分，纯单边仓位直接消失在结果中。当前 REST 快照未实现，该配对错误属于接通后的潜伏缺陷。

应使用真实 OTP 监督树，并从持久化订单和持仓恢复。实盘必须查交易所完成对账，未关联敞口显式保留，不能猜成套利组合；恢复期间禁止新开仓。

## 5. 推荐方案

| 方案 | 取舍 | 建议 |
| --- | --- | --- |
| 在现有开平仓链路逐点修补 | 单项较快，但状态副本和交接根因仍在 | 只适合临时阻断假成功 |
| 保留 OTP 和有效接入，重写执行及账本核心 | 范围可控，能消除根因，不重做无关页面 | **推荐** |
| 更换语言、整体重写 | 仍需解决相同交易问题，还要重验工具链和部署 | 不推荐 |

目标链路：

```text
交易所市场数据 -> 边界标准化 -> ETS 一致快照
一致快照 -> 纯函数机会计算 -> 账户额度检查和资金预留
资金预留 -> 套利组合状态机 -> 两腿订单适配
订单/成交/资金费回报 -> 精确归一化 -> 原组合状态机
组合状态机 -> 原子提交订单事实、持仓、逐腿账本
HTTP 查询 -> 独立展示转换，不参与决策或修改运行状态
```

### 职责与最小状态

- 一个组合从开仓到退出只有一个受监督 `gen_statem` 所有者，取代独立 open/close 执行器间的持仓交接。状态只保留恢复对账、开仓、持有、平仓、结束和需人工处置。
- 两腿订单状态、真实未对冲数量和未知提交结果分别记录，不用一个总进度代替。正常生命周期单一，不代表能删掉部分成交与单边风险处理。
- 账户进程负责不可变账户身份、共享额度和并发资金预留；组合进程不能直接改别的账户资金。
- 模拟与实盘只有成交来源不同，共用订单事件、数量算法和账本。两个真实实现需要明确接口，但不扩成通用插件框架。
- 沿用 Mnesia，订单状态、成交去重、持仓和余额在一次业务事务更新。先验证可写，再启动交易；只持久化当前需要的事实，不引入通用事件溯源框架。
- ETS 仍由 Application 启动路径初始化一次。简单键值用 tuple，复杂内部数据用 record；ETS 行情是缓存，不是资金或持仓的权威来源。

### 不可省略的约束

1. 下单意图和稳定客户端订单 ID 先落盘，未知结果先查询，不盲目重发。
2. 两腿独立记录订单、累计成交、均价、费用和终态；资金费按结算身份去重。
3. 合约张数、基础币数量、USDT 金额明确区分。仅支持已确认规格，在边界转换一次；数量和金额使用明确整数单位与精度，不靠浮点容忍判定全部完成。
4. 资金预留、单账户/单交易所限额、组合唯一性由共享资金所有者原子执行，不能只在扫描阶段估算。
5. 禁开仓后继续管理持仓；超时、断线和风险退出由独立定时器驱动。
6. 有单边暴露先处理已有风险，不能继续增加领先腿；补齐或减仓必须有价格容忍、时限和失败升级，禁止无限循环。
7. 重启先恢复及对账，未完成时不得新开仓。未知外部状态不能被默认值、旧缓存或 `catch` 变成可交易。

### 收敛利润和退出规则

先保留风险退出、达到完整交易净收益目标、继续持有预期净收益不足三类。删除重复价差阈值、资金费后相同阈值判断和 95/90/85/80/50 多段分支，除非回放数据能证明其必要性。

完整净收益采用逐腿价差盈亏 + 已到账资金费 + 已到账返佣 - 开仓费用 - 实际/预计平仓费用。未来资金费、未到账返佣和假设退出基差只属于预测。入场必须明确持有区间、带符号资金费事件、成本、滑点和退出基差假设；第一阶段只验收执行正确性，不宣称盈利。

## 7. 分阶段实施与验收

### 第一阶段：执行和账本可信

固定审查基线，将本轮异常转成正式 EUnit/CT 回归。先阻断假实盘受理，完成组合状态机、稳定身份、逐腿数量和幂等账本，然后删除旧模拟策略及开平仓交接。复用工具链和依赖，不重做无关前端。

验收：拒绝不崩溃，失败不标成交；重复、乱序事件不改最终数量；无重复扣款或保证金返还；逐腿资金守恒；分批和全量成交结果一致。

### 第二阶段：行情、风控、恢复可信

统一盘口和合约规格，修复连接代次和订阅恢复，落实新鲜度、风险定时器、资金费事件与账户监督；完成持久化恢复和就绪门禁。

验收：旧盘口、缺深度、断流、未对账时不开仓；单腿拒单或成交能受控处理；禁开仓后仍管理已有仓位；终止任一组合进程后恢复不重复下单；数据库不可写必须阻止交易。

### 第三阶段：有限实盘接入

仅实现用户实际需要的两家交易所与一种明确合约类型。核对当前签名、数量单位、精度、持仓模式、reduce-only、订单查询、资金费与成交协议；未实现的交易所不进入实盘可交易列表。

验收：真实/模拟适配器共用事件契约；覆盖认证失败、部分成交、单腿拒绝、提交结果未知、撤单竞态、断线补账、重启恢复。联网与真实账户操作另行取得授权，本方案不授权下单或部署。

### 第四阶段：收尾与运行验收

同次移除被替代模块、字段、旧接口和旧文档描述；管理端只反映真实状态。固定提交与构建产物，按实际影响范围发布并做运行验收，不以编译通过代替稳定性证明。

开发模拟数据仅在确认无需保留后按新结构初始化；配置、凭据、真实交易流水与资金账本不属于开发垃圾，不得随意清理。

## 8. 实施前确认项

建议继续 Erlang/OTP，以基础币数量中性的 USDT 线性永续为首个验收范围，这不是已确认需求。真实接入阶段需要确认实际两家交易所、合约和持仓模式，以及历史交易数据保留要求。没有这些确认，不扩大实盘能力，不替用户选择下单环境。
